# Elastic SIEM Implementation

## 1. Overview

The AI-Enhanced Network Security Platform uses Elastic Elasticsearch and Kibana as the Security Information and Event Management (SIEM) layer.

The SIEM provides centralized indexing, searching, visualization, monitoring, and presentation of security decisions generated by the project's AI/ML security pipeline.

The implementation connects the analytical security pipeline with a live Elasticsearch index and Kibana dashboard.

---

## 2. SIEM Architecture

The implemented security flow is:

**Network Traffic**

↓

**Zeek + Suricata**

↓

**Traffic and Security Data**

↓

**Python AI/ML Pipeline**

- Behavioral Analysis / UEBA
- Isolation Forest anomaly detection
- Automated Threat Hunting
- IOC Correlation
- Risk Scoring

↓

**Security Decision**

↓

**Dynamic Policy / Quarantine**

↓

**Elasticsearch**

↓

**Kibana SIEM Dashboard**

↓

**Security Analyst / SOC Monitoring**

---

## 3. Implemented Technologies

| Component | Technology | Purpose |
|---|---|---|
| Network monitoring | Zeek | Network protocol and connection analysis |
| IDS/IPS | Suricata | Signature-based threat detection |
| AI/ML | Python + scikit-learn | Behavioral analysis and anomaly detection |
| UEBA | Python | Behavioral baseline and deviation scoring |
| Threat hunting | Python | Automated investigation of high-risk activity |
| Threat intelligence | Local IOC dataset | IOC correlation and enrichment |
| Risk engine | Python | Combined risk calculation and response decision |
| Enforcement | iptables | Host-level quarantine enforcement |
| SIEM | Elasticsearch | Security event indexing and search |
| Visualization | Kibana | Dashboard and security monitoring |
| Evidence | CSV / Markdown | Investigation and audit evidence |

## 4. Elasticsearch Configuration

Elasticsearch was deployed as the central data store for security events.

The project uses the following index:

`ai-network-security`

The index is configured for the controlled laboratory environment with:

- 1 primary shard
- 0 replicas

The implementation was tested using Elasticsearch 9.5.5.

The index contains the security decisions generated by the AI-enhanced network security pipeline.

---

## 5. Python SIEM Ingestion

The project includes:

`src/elastic_siem_ingest.py`

This script reads:

`final_security_decision.csv`

and converts each security decision into an Elasticsearch document.

The main fields sent to Elasticsearch are:

- `@timestamp`
- `entity`
- `ueba_score`
- `ioc_matches`
- `combined_risk`
- `risk_level`
- `recommended_action`
- `source`
- `environment`

The Elasticsearch Python client is used to perform the ingestion.

---

## 6. Duplicate-Safe Event Ingestion

The ingestion script uses a stable document ID:

`<entity>-<recommended_action>`

For example:

`10.0.2.15-QUARANTINE`

This prevents repeated executions of the ingestion script from creating duplicate security events for the same entity and response decision.

The implementation was verified by repeatedly running the ingestion script and confirming that the Elasticsearch index contained **one authoritative security event**.

Elastic does not replace the project's AI/ML security engine.

Instead, Elasticsearch and Kibana provide the SIEM layer for storing and visualizing the decisions generated by the existing security pipeline.

The logical integration is:

**Zeek / Suricata**

↓

**Python Data Processing**

↓

**UEBA / Isolation Forest**

↓

**Threat Hunting**

↓

**IOC Correlation**

↓

**Risk Engine**

↓

**Security Decision**

↓

**Elastic SIEM**

↓

**Kibana Dashboard**

This separation allows the AI/ML components to perform detection and analysis while Elastic provides centralized security-event storage, search, visualization, and monitoring.

The risk engine can generate a recommended response such as:

The enforcement concept is:

**High Risk**

↓

**QUARANTINE Decision**

↓

---

## 14. Security Monitoring Workflow

The overall monitoring workflow is:

1. **Detect** network activity using Zeek and Suricata.
2. **Analyze** traffic and behavioral characteristics.
3. **Establish behavioral deviation** using UEBA and anomaly analysis.
4. **Hunt** for additional evidence associated with high-risk behavior.
5. **Correlate** activity against the IOC dataset.
6. **Calculate risk** using the risk engine.
7. **Generate a response decision** such as QUARANTINE.
8. **Apply host-level enforcement** where required.
9. **Index the security event** in Elasticsearch.
10. **Visualize the event** in Kibana.
11. **Investigate and respond** using forensic and incident-response evidence.

## 16. Laboratory Scope and Limitations

The SIEM implementation was developed and tested in a controlled laboratory environment.

Important limitations are documented to avoid overstating the implementation:

- Elasticsearch and Kibana provide the SIEM/search/visualization layer.
- The AI/ML processing remains implemented in Python.
- The IOC dataset is locally maintained for laboratory testing.
- The UEBA score represents behavioral deviation, not attack probability.
- The combined risk value is a normalized laboratory risk score.
- TLS analysis uses traffic metadata and does not decrypt encrypted payloads.
- The current enforcement mechanism is host-level iptables enforcement.
- SDN-style policy generation is implemented, but a production SDN controller and VLAN automation are not claimed.
- The controlled ML evaluation uses synthetic anomalies and should not be interpreted as real-world production accuracy.

---

## 17. Security and Credential Handling

Elasticsearch authentication is performed using the `elastic` account.

Credentials are not stored in the GitHub repository.

The local ingestion configuration uses certificate verification disabled for the controlled laboratory Elasticsearch HTTPS connection.

This configuration is suitable for the current isolated laboratory demonstration but should be replaced with proper certificate validation and secure secret management in a production deployment.
